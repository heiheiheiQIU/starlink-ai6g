# B → C 原包与第二台电脑验收交接

本轮响应审计图片指出的三项缺口。B 补交原始离线 ZIP 和验收资料；C 需在自己的电脑独立复算原包哈希并实际运行。没有第二台电脑的真实记录时，第二机状态保持 pending。

## 原包与身份

原包现位于仓库 [deliveries/B_final_demo_20261110.zip](../../deliveries/B_final_demo_20261110.zip)，17,532,109 字节，SHA256 为 `8b79351f35447fd8764451bfa0151447316dbd90f16b0be1d8f15bbd212664f4`。文件和上轮本地交付原包逐字节相同，运行版本仍为 fc44e25。请取此文件，不要把 GitHub 整仓源码下载 ZIP 当作离线演示包。

B 已重新检查 ZIP CRC、全部 110 个载荷文件 SHA、来源版本和模型权重 SHA。记录见 [B 原包检查](../evidence/B/offline_handoff_2026-11-10/B_original_package_check.json)。这些检查是 B 的补交付自验，不能填写为 C 的独立结论。

## C 实机验收步骤

1. 在 C 自己的 Windows x64 电脑取得原包，用 Get-FileHash 独立计算 SHA256，并记录电脑说明、时间和实际值。将结果与 deliveries 中的 .sha256 比较。C 机器不满足 Python 3.12 前提时，先记录缺项。
2. 按 [原包 README](../../deliveries/README.md)解压到新目录并运行 accept.py。它会检查包完整性、离线安装与 pip check、页面资源、五组真实运行、分页事件、导出及确定性复跑。保留 acceptance 下完整结果，失败保留原日志，不覆盖挑选。
3. 启动 start.py，进入“场景验证”的“交互仿真沙盒”，选择 EDF vs Learned、seed=7，逐项实际运行并记录新 run_id。
4. 完成下表手工检查并留截图；最后填写 [C 回执模板](../evidence/B/offline_handoff_2026-11-10/C_receipt.template.json)的副本。没有检查的项目保持 pending，不填 accepted。

| 检查项 | 通过依据 | 应保存的证据 |
|---|---|---|
| S1 资源充足 | 新 run_id 完成；EDF 100%、Learned 0%，能量违规均 0 | run_id、结果截图、导出 ZIP |
| S2 健康临界 | 与 S1 不同 run_id；两者均 0%，能量违规均 0 | run_id、结果截图、约束原因 |
| S3 强扰动 | 又一个独立 run_id；EDF 100%、Learned 0%；EDF 事件有 ACK_TIMEOUT、DUPLICATE_BLOCK | run_id、事件截图、导出 ZIP |
| 参数变化 | 修改一个轴后提示旧结果；重新运行后生成新 run_id，输入/配置哈希与实际请求对应 | 参数变更前后、run_id 与哈希 |
| 结果失效提示 | 改参数且未重跑时明确提示下方仍为历史结果 | 截图 |
| 跨页面与策略分流 | “策略评估”“结果追溯”保持当前 run_id；EDF/Learned 回放各用自己的时钟 | 两页面截图与策略选择 |
| 事件分页 | 自动验收每页 7 条排空、ID 连续、最终事件与 ZIP 一致；手工确认回放可用 | golden/verification.json、各场景 events.json 与 export.zip |
| 页面导出 | 点击当前运行下载按钮，下载成功；ZIP 身份和当前 run_id 一致 | 实际下载文件、SHA256、manifest.json |
| 材料口径 | 工程闭环可验收；Learned 负结果如实保留；正式结果发布状态独立判断 | 录屏或报告对应说明 |

## C 回传材料

- C 独立原包哈希记录和填妥的 C_receipt.template.json 副本，说明是否确实在另一台物理电脑运行。
- 整个 acceptance 目录，包括 install.log、launcher.log、golden.log、acceptance.json 和五组事件/结果/导出。
- 页面手工检查截图以及实际下载 ZIP。异常时附错误日志与操作顺序，不删除失败记录。
- 可以提交到 C 的审计分支或交回本项目；不要将模板中的 expected 值复制成 actual 值来代替计算。
